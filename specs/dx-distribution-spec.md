## 1. Product Manager section

### 1.1 Business logic

Nothing here adds a component. It is all distribution: making the 163
components that already exist findable, understandable, and trivially
copyable. This is the bundle with the highest ratio of impact to effort,
because it multiplies the value of everything already built.

### 1.2 Why the customer wants this

- **`llms.txt`** — for a copy-paste library, a large share of usage now flows
  through an AI assistant. If Cursor/Copilot/Claude generate *correct*
  shadcn-angular code on the first try, adoption compounds; if they hallucinate
  a React API, the developer blames the library. An MCP server already exists,
  but there is no stable, fetchable usage corpus.
- **A real docs site** — Storybook and the demo app are two half-answers.
  Neither gives the canonical "one page per component: install command, live
  preview, copy-paste code, API table". The API table is nearly free:
  `documentation.json` (compodoc) is already generated by `npm run docs:json`
  and currently only feeds Storybook autodocs.
- **StackBlitz + the install command on every demo page** — time-to-first-render
  is the metric that decides adoption. Today a developer who likes a demo has
  to go find out how to install it.
- **`why` install size** — `why` already prints file count and reverse
  dependents but not bytes. A developer deciding whether to add a component
  wants the cost.
- **Theme playground** — `set-density`, `set-radius`, `set-motion` and
  `change-theme` all exist as CLI commands with no visual front-end. This is
  the artifact people screenshot and share.
- **Recipes** — developers copy *patterns*, not components.
- **Version matrix** — the README currently says Angular 21 and "further
  versions have not been tested", which reads as unmaintained.

### 1.3 Use cases — definition of done

| ID | Use case |
|---|---|
| UC-1 | A stable `llms.txt` is published at a predictable URL, listing every component with a one-line description and a canonical usage snippet. |
| UC-2 | An AI assistant given only `llms.txt` produces a *compiling* usage of three sampled components. |
| UC-3 | Each component has a docs page with: install command, live preview, copy-paste code, and an API table (inputs/outputs/types). |

### 1.5 The publish question — Task 1 decides it

Per `.claude/CLAUDE.md`, an npm publish is required **only** when the bundled
CLI logic, the `ComponentDefinition` manifest *shape*, or the utils baselines
change. Registry *data* and component source are served live from `master`.

**UC-7 changes `packages/cli/src/commands/why.ts` — that is CLI logic, so it
requires a publish.** Everything else here (docs, demo app, `llms.txt`) does
not.

Task 1 confirms this against `packages/cli/src/registry/load.ts` and
`core/fetch.ts` rather than assuming, and reports. Publishing is **manual and
2FA-gated — the agent must never run `npm publish`.** Do the work up to it,
then hand off to the user, and add the PR to the pending-releases memory.

### 1.6 Out of scope

- Running the publish (manual, passkey/2FA — hand off).
- Any component source change.
- A new docs framework if the demo app can host the pages (see §3.4).
- Figma kit.

### 2.2 T-3 is the test that matters

`llms.txt` is only worth shipping if the code it teaches actually compiles.
Take three components at random, feed **only** their `llms.txt` entry to a
fresh generation, and build the result in the e2e fixture app. If it does not
compile, the corpus is actively harmful — it will confidently produce broken
code at scale.

Similarly T-11: a playground that emits CSS differing from what
`set-density`/`set-radius` produce is worse than no playground, because the
developer's pasted CSS then fights the CLI.

### 2.3 Edge cases

Component with no inputs; component with generic types (`<T>`); addon entries
with a `/` in the name (`data-table/export`); directives (attribute selectors,
not elements — the snippet form differs); components whose demo route differs
from their registry name.

### 2.4 Coverage expectation

New generator scripts and CLI changes ≥90% lines. Docs pages are generated —
assert the generator, not each page.

## 3. Architecture

### 3.1 Usability / DX

The whole bundle *is* DX. Guiding rule: **anything a developer reads must be
generated from a single source of truth**, so it cannot drift. The registry is
the source for names/deps/descriptions; `documentation.json` is the source for
API tables. Nothing hand-maintained per component.

### 3.2 Efficiency

Generators must be fast enough to run in the pre-push hook or a docs build —
budget under 10s for the full set. Generate to disk; do not compute at runtime.

### 3.3 Implementation options — where the docs site lives

**Option 1 — A new standalone docs site** (Astro/Docusaurus/etc.).
Pros: purpose-built, best long-term. Cons: a whole new app to build, deploy and
maintain; **adds dependencies**, which cuts against the project's identity; and
duplicates the demo app's existing 113 routes.

**Option 2 — Extend the existing demo app** with a docs layout: each existing
demo route gains install command, code block, and a generated API table.
Pros: reuses 113 working routes and the existing Netlify deploy; zero new
infra; the live preview already exists — it *is* the demo. Cons: the demo app
takes on a second job.

**Option 3 — Storybook autodocs only.**
Pros: already wired to `documentation.json`. Cons: Storybook is a component
workbench, not a docs site; no install commands, poor SEO, and developers do
not read Storybook as documentation.

**✅ Chosen: Option 2.** The demo app already has the two expensive things — a
route per component and a working live preview. Adding a docs layout to it is
days of work; a new site is weeks, plus permanent maintenance and new
dependencies. Revisit only if the demo app becomes the constraint.

### 3.4 Implementation options — `llms.txt` generation

**Option 1 — Hand-write it.** Guaranteed to drift the moment a component
changes. Rejected outright.

**Option 2 — Generate from `registry.json` + `documentation.json`,** with a
per-component usage snippet sourced from the component's existing Storybook
story or demo page.
Pros: single source of truth; T-2 can assert zero drift; new components appear
automatically.
Cons: needs a convention for which story is "canonical".

**✅ Chosen: Option 2.** Add a `docs:llms` script alongside the existing
`docs:json`, and assert in CI-less local gates that the committed file matches
a fresh generation (T-2) — the same discipline the registry already uses.

### 3.5 Risks

| ID | Risk | Mitigation |
|---|---|---|
| R-1 | `llms.txt` teaches code that does not compile | T-3 compiles sampled snippets in the fixture app |
| R-2 | Playground CSS diverges from CLI output | T-11 asserts they match for the same settings |
| R-3 | `why` change forces an npm publish the user did not want | Task 1 confirms and **asks** before implementing UC-7; it can be deferred without blocking the rest |
| R-4 | Generated docs drift from source | Everything generated; T-2/T-5/T-6 assert regeneration equality |
| R-5 | Agent runs `npm publish` | **Never.** Publishing is manual and 2FA-gated. Hand off and record in pending-releases memory |
| R-6 | Scope explodes into a full docs platform | Option 2 chosen precisely to bound this. New infra ⇒ STOP and report |

## 4. Definition of Done (per task)

A task row may be marked ✅ Done only when **all** of these pass:

1. **Fully tested** — every test named for this task is written and passing.
2. **Fully covered** — no uncovered lines introduced in the files touched.
3. **Zero lint errors** — `npm run lint` clean.
4. **Zero SonarQube issues** — full server scan (`npm run coverage` then
   `unset SONAR_TOKEN; npm run sonar`) clean on changed code. If
   token/server/Docker unavailable, the task is **blocked, not done**.
5. **Review gate ≥ 91** — invoke the `review-gate` skill.

Then update the task row with **Completed**, **Score**, **Retrospective**.
